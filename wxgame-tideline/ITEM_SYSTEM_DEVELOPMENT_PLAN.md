# 微信端道具系统开发方案

版本：v0.1（开发草案）

日期：2026-09-13

适用工程：`wxgame-tideline`

本轮交付：开发方案；尚未实现业务代码。

后续实现已完成，实际行为、广告配置与验证说明见 [ITEM_SYSTEM_IMPLEMENTATION.md](./ITEM_SYSTEM_IMPLEMENTATION.md)。以下保留初版设计记录。

## 1. 已确认需求与首版范围

| 项目 | 已确认内容 |
|---|---|
| 道具种类 | 通勤喇叭、延时车票，共 2 种 |
| 新手赠送 | 新玩家首次进入，每种赠送 1 件 |
| 广告获取 | 观看一次完整激励视频，自选 1 件 |
| 分享获取 | 分享好友后返回即可领取，自选 1 件；按参与奖励处理，取消分享也可能领取 |
| 使用方式 | 所有奖励先进入背包，由玩家手动使用，不自动生效 |
| 界面 | 增加背包入口、关前道具展示、局内快捷按钮、补给弹窗与结算补给入口 |

分享路径已经确定为“分享返回领取”，不要求好友进入、领取或完成助力。界面和技术实现均不能宣称验证了实际转发成功。

首版不增加咖啡、金币、随机抽奖、道具升级、付费购买、原地复活或好友赠礼后端。正常开始游戏、重试和下一站保持现有流程。

以下数值属于本草案的建议默认值，可在体验测试后调整，不等同于用户已确认的固定限制：

| 参数 | 草案默认值 |
|---|---|
| 通勤喇叭目标数 | 最多 4 人 |
| 通勤喇叭范围 | 当前关卡普通疏导范围 × 1.25 |
| 通勤喇叭侧移 | 当前关卡普通疏导侧移 × 1.5 |
| 通勤喇叭效果时长 | 0.5 秒 |
| 延时车票 | 增加 3 秒关门时间 |
| 战役使用额度 | 每局每种最多 1 次，即合计最多 2 件 |
| 无尽使用额度 | 整场每种最多 1 次；通过下一轮不重置，重新开始整场才重置 |
| 获取次数 | 首版暂不设置产品侧每日领取上限；保留配置入口，广告供应仍受平台限制 |
| 库存显示 | 真实数量持久化；小按钮超过 99 时显示 `99+`，背包展示完整数量 |

## 2. 当前代码基础与改造约束

工程采用 `core → runtime → render / platform` 分层，继续沿用原生 Canvas 和现有构建流程。

| 当前实现 | 对本次开发的影响 |
|---|---|
| `core/ability.ts` 普通疏导实际限制最多 2 人、冷却 1 秒 | 通勤喇叭必须使用独立参数，不能修改全局常量后连带增强普通技能 |
| `core/simulation.ts` 使用固定步长、种子随机数和事件记录 | 道具在模拟步边界生效，不能让异步广告回调直接修改游戏世界 |
| `core/phase-machine.ts` 私有字段管理倒计时 | 延时需要状态机正式接口，不能直接修改 `GameState.doorRemaining` |
| `startedEventIds`、`closedDoorIds` 管理已触发事件和永久封门 | 延时不能重播事件、恢复封闭车门或回退整局时间 |
| `save-schema.ts` 当前版本为 3 | 增加 v4 迁移，覆盖全部存档清洗和复制路径 |
| 微信存储键为 `tideline.save.v1` | 保持存储键不变，只升级数据内部版本，避免旧进度丢失 |
| `WxStorageAdapter.load()` 对异常统一回退空存档 | 增加读取状态信息，区分首次进入与存档读取失败 |
| `GameRuntime.recordResult()` 有单次结算保护 | 增加道具使用记录，继续防止重复累计局数、成绩和奖励 |
| 暂停目前由页面、用户暂停、生命周期共同控制 | 新增弹窗及奖励流程暂停原因，防止广告返回提前恢复 |
| UI 绘制和触摸区域通过布局数据连接 | 两个道具按钮及所有弹窗必须共用布局计算结果 |

本方案编写时，工作区已有游戏规则、角色表现及测试方面的未提交修改。本轮只新增本文件；后续实现以届时工作区代码为准，不覆盖已有修改。

## 3. 道具规则

### 3.1 通勤喇叭 `commute-horn`

面向玩家的描述：**“疏通前方最多 4 名乘客，帮你挤出通行空间。”**

1. 允许在 `positioning`、`exiting`、`boarding`、`warning` 使用。
2. 按玩家朝向筛选前方目标，复用普通疏导的目标资格、稳定排序和礼让计算；最多影响 4 人。
3. 范围、侧移和时长使用第 1 节配置；重叠修复、车门和场景边界继续由现有规则约束，不允许穿过封闭车门或墙体。
4. 不消耗体力；不受普通疏导冷却限制，也不重置普通疏导冷却。
5. 无可作用目标、阶段不允许、正在暂停、库存不足或额度耗尽时不扣库存，并显示具体原因。
6. 成功使用计入疏导次数和礼让计算；另外记录道具次数。不能借助道具绕过“疏导次数”目标。
7. 同一模拟步同时收到普通疏导和道具命令时，优先处理成功的道具命令，避免一次手势引起两个疏导效果。
8. 视觉使用扩大的喇叭声波和乘客让行动作；一次使用只播放一次反馈音效。

实现建议：抽取可配置的目标选择及侧移逻辑，普通疏导与喇叭分别提供参数、消耗规则和事件类型。保留普通技能现有行为的回归用例。

### 3.2 延时车票 `delay-ticket`

面向玩家的描述：**“关门倒计时增加 3 秒，为上车争取时间。”**

1. 只允许在 `boarding`、`warning` 且尚未结算时使用。
2. 在 `PhaseMachine` 增加受校验的延时接口，将剩余时间增加 3 秒，并同步至模拟快照。
3. 若处于 `warning`，延时后高于警告阈值，则回到 `boarding`；之后下降到阈值时重新进入警告。渲染与实际规则必须一致。
4. 保持总经过时间、人群位置、随机数、已触发事件和封门集合不变；关卡事件不会随延时整体后移。
5. 已被提前关门事件封闭的门继续关闭，其他开放门正常运行。
6. 到零结算前已排入有效模拟步的命令可生效；已经进入 `result` 的命令拒绝执行，不支持结算后续命。
7. 使用后显示 `+3 秒`，更新倒计时和警告表现；不直接判定通关。

### 3.3 使用额度与成绩

库存属于长期存档，使用额度属于当前游戏会话，两者分别维护。战役重试重置本局额度，但不退还正常使用的道具；无尽下一轮只重置本轮效果，不重置整场额度。

建议保留现有通关、星级、成就和解锁体验：使用道具仍然可以正常通关及更新综合最佳成绩。结算新增“本局使用道具”记录，另存无道具最佳分、星级和无尽纪录，供路线页或未来榜单区分。

v3 历史成绩来自尚无道具的版本，可初始化为无道具成绩。无尽整场一旦使用道具，后续轮次均属于使用过道具的同一场挑战，不能中途恢复为无道具纪录。

## 4. 获取、入包与异常处理

### 4.1 新玩家首次赠送

流程：

```text
读取存档及读取状态
  → 确认为首次进入
  → 一次写入：喇叭 +1、车票 +1、首礼已发标记
  → 写入成功后展示新手赠送弹窗
  → 玩家选择“知道了”或“查看背包”
```

- 弹窗只告知已入背包，不自动使用道具；关闭弹窗不影响已保存的库存。
- 首礼库存与标记必须同一次存储写入，不能先标记已领取、再分别增加两种道具。
- 保存失败时不显示“领取成功”，提供重试保存；恢复后仍使用同一笔首礼标识。
- 只有确认存储键不存在才按新玩家处理。读取异常、损坏存档、未来版本不自动当成新玩家发礼。
- 已有有效 v3 及更早版本存档迁移时库存为 0，标记为非新手，不默认补发首礼；如后续需要老玩家补偿，另设一次性活动标记。
- 本地版“首次”限定当前设备存档。清除数据、重装或换设备无法可靠判断是否同一玩家，首版不承诺账号级唯一领取。

### 4.2 自选补给公共流程

```text
打开补给弹窗
  → 选择通勤喇叭或延时车票
  → 选择“看视频领取 ×1”或“分享好友领取 ×1”
  → 创建唯一请求并冻结所选道具
  → 完成对应领取流程
  → 统一发奖入口将 1 件道具写入背包
  → 显示领取结果
  → 玩家返回游戏后自行使用
```

- 从空库存快捷按钮进入时，预选对应道具，仍允许在发起前切换。
- 从背包、关前或结算入口进入时，明确展示两种道具供选择。
- 请求开始后禁止改选、重复点击或并行发起第二个广告／分享请求。
- 获取与局内使用额度独立；即使本局已经用过该道具，也可以在背包中为后续关卡补充。
- 发奖基于请求开始时冻结的道具 ID，不能读取回调时可能变化的 UI 选中项。
- 切换页面不会改变奖励归属；有效奖励进入长期背包，不作用于旧局或新局。

### 4.3 激励视频

新增 `WxRewardedAdAdapter`，封装可注入的微信广告能力。广告位 ID 由运行配置传入，不写入纯规则层。

- 提前创建并加载广告；仅玩家点击明确的领取按钮时展示。
- 使用 `onClose` 的完整观看结果作为领取依据；针对首版支持的基础库，要求 `res?.isEnded === true`。缺少结果字段不默认判成功。
- `show()` 成功、`onLoad`、普通 `onShow` 均不作为发奖依据。
- 中途关闭不发奖，保留选中道具，可重新观看或返回。
- 广告缺失、未配置广告位、API 不支持、无填充或网络错误显示具体可恢复状态；可提供分享入口，不自动替玩家执行分享。
- 展示失败可先 `load()` 再重试 `show()` 一次；仍失败即退出本次流程，不无限重试。
- 每个广告实例集中绑定监听；重复回调、旧回调和销毁后回调不能重复发奖或改变游戏状态。

### 4.4 分享返回领取（已确定采用）

这是**参与奖励**：玩家发起分享后返回，允许领取所选道具；不检查好友是否收到，不要求好友点击，不区分用户是否最终取消发送。

1. 在补给弹窗中点击“分享好友领取 ×1”，创建独立的 `requestId` 并冻结所选道具。
2. 检查分享 API 可用后调用 `wx.shareAppMessage`，分享内容使用通勤主题图片与真实游戏文案。
3. 若本次观察到 `onHide → onShow`，仅在当前仍有已发起的分享请求时进入领取状态；普通切后台不会生成奖励。
4. 平台若没有完整触发前后台回调，分享面板关闭后允许玩家点击原弹窗的“领取所选道具”。该点击仍按参与意愿领取，不作为分享成功凭证。
5. 正常回前台可展示领取结果；需要手动领取的兼容路径使用相同发奖入口。两条路径不能各发一次。
6. 分享 API 缺失或同步调用异常时终止请求并提示，不能伪造分享完成。
7. 不使用离开时长、随机概率、“请换个群重试”等方式判定或阻挡发奖。
8. 分享请求在进程被终止后不自动恢复为已完成；保留既有库存，重新进入后可重新发起参与。

推荐界面说明：“分享返回后可领取 1 件道具。”成功提示：“已领取，放入背包。”不使用“已验证分享成功”或虚构“分享失败”。

这一产品选择接受取消分享仍可领、重复参与可累计库存的行为。具体分享激励活动及文案仍需与正式发布时的微信运营规范匹配；不能将普通分享 API 的可用性视为平台对活动的审核结论。

### 4.5 统一发奖与使用提交

建议新增 `RewardService` 和道具使用编排入口，所有库存变更通过它们完成。

**发奖：**

- 每次请求具有唯一 ID、来源和冻结的道具 ID；发放数量固定为 1，新手礼为一笔包含两件的独立奖励。
- “库存增加”和“请求已处理”同一次存储写入。保存成功后才发布新内存存档、更新界面并提示成功。
- 已确认观看完成但写入失败时，当前会话保留该笔待保存奖励，允许只重试保存，不要求再看广告。
- 奖励状态可采用 `idle → requesting → claimable → saving → granted`，取消、不可用和保存失败分别处理。
- 任何晚到的重复回调都要先核对当前请求和处理状态；不能仅依赖一个无来源的布尔值。

**使用：**

- 在模拟步边界校验阶段、库存、额度和有效目标，生成效果计划；暂停期间不会执行使用计划。
- 准备扣减后的存档及 `pendingUse`，写入成功后才在同一步同步应用效果和增加局内使用次数。存储失败则不应用效果。
- 效果应用后清除 `pendingUse`；同一次命令不得重放。对可预期的无目标和无效阶段，必须在扣库存前拒绝。
- 若进程在扣减与完成标记之间退出，因首版不保存对局，下一次启动对未完成的 `pendingUse` 一次性返还道具，再清除记录。
- 上述恢复策略优先避免吞道具，接受极小窗口内效果已发生但完成标记未落盘时的补偿；不宣称本地存储可实现跨进程绝对原子提交。

本地方案不具备防篡改或服务端广告凭证恢复能力。广告完成后尚未来得及成功写入任何结果就被系统终止的情况，不能保证自动补发；如后续需要账号级库存与强恢复，再单独接入云存档及服务端奖励核验。

## 5. 界面与交互

### 5.1 首页及通勤背包

- 首页增加“通勤背包”入口，沿用现有 Canvas 菜单风格。
- 背包展示两张道具卡片：图标、名称、库存、效果、使用阶段、“获取道具”按钮。
- 首页背包不显示“立即使用”，避免在关外误消耗。
- 背包入口还可从关卡说明页和结算页打开；记录来源页面，关闭后返回原位置，不统一跳首页。

### 5.2 关卡说明页

- 保留关卡说明和“确认并开始”。
- 增加一行：`通勤喇叭 ×N    延时车票 ×N    [补充道具]`。
- 提示“道具进入关卡后手动使用”，不增加装备或携带确认步骤。
- 新手首次看到时说明：喇叭用于疏通人群，车票在上车倒计时阶段使用。

### 5.3 局内快捷使用

主布局示意，具体位置按安全区与画布尺寸计算：

```text
┌──────────────────────────────────────┐
│ 关卡 / 倒计时 / 体力           暂停   │
│                                      │
│            车厢与站台场景            │
│                                      │
│                           喇叭  车票 │
│   摇杆                       疏导    │
└──────────────────────────────────────┘
```

- 在普通疏导按钮上方布置两个较小快捷按钮；显示图标、简称和数量。
- 有库存且允许使用：点击直接使用，并显示声波或 `+3 秒` 反馈。
- 库存为零且当前阶段允许：点击暂停并打开补给弹窗，不直接播放广告或调起分享。
- 阶段不允许：保留按钮位置，显示不可用状态；点击提示“上车倒计时开始后可用”等具体原因。
- 本局额度用完：显示“本局已用”；无尽显示“本场已用”。不将此状态误判为空库存并引导补给。
- 暂停／弹窗期间禁用局内快捷使用。多指操作需兼容左手摇杆、右手道具，不能留下粘连输入。
- 绘制和命中共用布局；横屏窄屏不覆盖疏导按钮、车门关键信息和系统胶囊安全区。逻辑触摸区域建议不小于 44 × 44。

### 5.4 补给弹窗

```text
补充通勤道具

[ 通勤喇叭 ×N ]    [ 延时车票 ×N ]
 当前所选道具效果说明

[ 看视频领取 ×1 ]
[ 分享好友领取 ×1 ]
[ 返回 ]
```

- 两种途径具有相同奖励数量；开始前明确展示道具名称。
- 视频加载中、视频播放中、等待分享返回、保存中、保存失败、领取完成分别显示对应状态。
- 领取完成后显示“已放入背包”，主按钮为“继续游戏”或“返回背包”，不把领取与使用合并。
- 因分享回调缺失需手动领取时，弹窗提供“领取所选道具”，与自动返回路径共享去重机制。

### 5.5 结算页

- 成功和失败结算均可显示当前库存及“补充道具”入口。
- 失败后普通“重试”保持直接可用；补给是可选操作。
- 展示本局使用过的道具与次数；无道具通关显示“无道具通关”。
- 补给完成后仍停留在结算页，由玩家选择重试、下一站或返回路线。

## 6. 暂停、声音与异步生命周期

建议将暂停原因合并管理：`user`、`lifecycle`、`modal`、`reward`。只要有一个原因存在，就不推进模拟。

| 场景 | 行为 |
|---|---|
| 局内打开背包／补给 | 暂停倒计时、人群、事件、体力恢复、技能冷却；释放当前触摸 |
| 播放广告／进入分享 | 持续暂停；按音频适配能力暂停游戏声音，不修改用户持久化音量设置 |
| 普通 `onShow` | 只解除生命周期暂停，不能解除弹窗或奖励流程暂停 |
| 奖励完成或取消 | 显示结果／原补给页，保持暂停，等待玩家返回或继续 |
| 原本已手动暂停 | 关闭补给仍保持手动暂停，不替玩家自动恢复 |
| 玩家明确继续 | 解除本流程暂停，清空旧触摸和过期帧间隔，再按固定步长运行 |
| 页面切换、重试 | 清理旧局使用命令；已有效完成的奖励仍只进入长期背包 |
| 运行时销毁 | 解除监听，拒绝过期回调；已落盘库存保留 |

获取流程计时与模拟时间分离，不能因广告播放很久而补算一大段游戏时间。

## 7. 数据结构与模块职责

以下为接口方向，具体类型在实现时与现有 `types.ts` 合并。

存档 v4 新增 `items` 和无道具成绩字段。数量必须为有限非负整数；未知道具 ID 不进入库存。正常的数值、星级更新及存档清洗不得丢掉新增字段。

近期请求 ID 记录设置有界容量；较老回调即使不在记录内，也必须因当前请求不匹配而被拒绝。`runId` 与奖励请求 ID 由运行时生成，不消耗游戏种子随机数，避免影响确定性回放。

## 8. 开发顺序与交付标准

| 阶段 | 工作内容 | 可检查交付物 |
|---|---|---|
| P1：存档与背包基础 | v4 迁移、读取状态、首礼、库存、基本查询 | 首次进入各 1 件；重启不重复发；旧进度保留 |
| P2：道具规则 | 喇叭、延时状态机、单局／整场额度、使用提交 | 两种道具可通过测试输入使用，普通技能及关卡回归通过 |
| P3：完整界面 | 首页背包、关前展示、快捷按钮、补给弹窗、结算 | 不依赖广告也可用新手礼完成完整道具流程 |
| P4：获取接入 | 统一奖励服务、广告、分享参与奖励、去重和异常 | 两途径均可自选领取 1 件并先入包；取消与重复回调符合规则 |
| P5：成绩与集成 | 无道具记录、暂停／音频／生命周期、无尽模式 | 广告或分享返回不偷跑、不自动使用、不串局 |
| P6：验收与发布准备 | 自动化回归、真机、资源及包体检查、运营配置 | 验收表有记录，未完成的真机或后台依赖明确标记 |

P1–P3 可用新手礼和测试中注入的 mock 奖励验证；生产构建不包含任意加道具按钮或无条件广告成功模拟。

首版广告联调需要正式可用的激励视频广告位 ID，并确认最低基础库及目标设备。未提供广告位时可继续完成规则、界面、分享和 mock 测试，广告入口展示不可用原因；不能将 mock 通过写为真实广告接入完成。

## 9. 验收清单

### 9.1 自动化验收

| 类别 | 必测行为 |
|---|---|
| 首次赠送 | 新存档两种各 1；保存失败可重试；重启／重复初始化不重复发；读取失败不误发 |
| 迁移 | v3 进度与设置不丢；旧存档库存为 0；未来版本／损坏数据处理清晰；所有清洗路径保留道具字段 |
| 喇叭 | 最多 4 个合法目标；无目标不扣；体力和普通冷却不变；礼让与统计正确；普通疏导仍最多 2 人 |
| 延时 | 剩余时间准确 +3；警告退出再进入；不回退总时间、不复活封闭门、不重播事件；结算后拒绝 |
| 使用提交 | 双击只用一次；不足／保存失败不生效；未完成使用启动补偿只执行一次 |
| 视频领取 | 完整观看发 1；提前关闭、缺结果、加载失败不发；重复和过期回调不重复发 |
| 分享领取 | 返回可领；取消分享后返回也可领；缺回调可手动领；两条路径只发一次；普通切后台不发 |
| 自选冻结 | 两种道具可选；请求开始后不能改奖励目标；广告与分享不能同时请求 |
| 保存重试 | 已完成请求只重试落盘，不再次要求广告；确认保存前不显示领取成功 |
| 生命周期 | 倒计时、人群、事件、恢复量和冷却全冻结；返回保持弹窗；原用户暂停不被覆盖 |
| 输入／布局 | 摇杆与道具多指并行；弹窗不穿透；暂停不消费；绘制与命中一致；横竖屏与安全区适配 |
| 战役／无尽 | 战役重试额度重置；无尽下一轮额度不重置；新开整场才重置；获取库存不自动使用 |
| 成绩 | 使用道具仍能解锁；无道具纪录独立；无尽使用标记延续整场；结算统计不重复 |
| 确定性 | 同种子、相同道具命令序列得到相同模拟结果；广告和请求 ID 不改变游戏 RNG |

### 9.2 真机走查

1. 新安装首次进入，领取两种赠品、使用、退出再进入核对库存。
2. 在最后几秒打开补给，观看完整广告，返回后确认倒计时未减少且道具未自动使用。
3. 提前关闭广告、无填充、断网、连续点击领取，检查失败提示和库存。
4. 分享给好友后返回、取消发送后返回，以及未触发完整生命周期时的手动领取。
5. 广告／分享期间再次切后台、恢复、重试或销毁运行时，检查暂停与过期请求。
6. iOS、Android、开发者工具及支持的 PC 场景分别记录能力差异，不能以开发者工具表现代替真机。
7. 横屏安全区与窄屏检查两个道具按钮、领取弹窗、摇杆和疏导的实际命中。
8. 连续进行无尽轮次，确认额度和“使用过道具”标记不被新轮模拟器清空。

## 10. 发布配置与资料

- 配置正式激励视频广告位 ID、能力开关及随包分享素材；未配置的能力不展示为可领取。
- 本方案默认不要求服务端、登录或好友资料；将分享返回视作参与，不收集通讯录、群成员或好友领取记录。
- 核对新增能力与现有 `M7_COMPLIANCE_CHECKLIST.md`、隐私声明和发布审计。对审计命中的实际新增能力逐项解释，不能删除检查或全局忽略告警。
- 分享奖励的实现、说明与后台现行规则需要一致；本方案没有将用户接受取消领取等同于平台审核通过。
- 首版只记录必要的本地事件：领取来源、结果、道具 ID、使用阶段、是否通关。后续若接入在线统计，再独立定义传输数据与配置。
- 平衡观察优先比较喇叭／车票使用率、有无道具通关表现、领取后是否继续游戏；首版不据此自动改变难度。
