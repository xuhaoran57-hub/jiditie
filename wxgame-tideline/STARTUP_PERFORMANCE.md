# 微信启动优化

本次针对报告中的代码包下载 1016ms、首屏渲染准备 632ms 优化。环境加载 3490ms 和框架加载 715ms 需在同一机型、微信版本、基础库、网络和缓存条件下复测，不能用本地测试推算其改善。

## 已落地

- BGM 从 814,198 字节 WAV 转为 222,563 字节 MP3（96kbps、22050Hz、单声道）。保留原始 WAV 和编码延迟/填充信息；本地完整解码后的有效采样数与源文件一致，407,077 个采样、18.462 秒。
- 发布配置排除 BGM 源 WAV、SVG 源稿、已合并的 slow/phone/group 独立 PNG、开发说明与配置文件；源文件仍保留在仓库。
- 首页、路线和关卡介绍不再创建模拟器或拷贝乘客状态，确认进入游戏才创建关卡模拟。
- 首页先绘制；首轮帧回调建立时间基线，后续三帧依次处理欢迎礼包保存、角色图集加载和广告预加载。提前进入关卡/外观页或点击广告时可按需加载，预加载保持幂等。
- 新用户礼包保留保存成功才发放、失败可重试的行为。同步读存档及未完成道具事务恢复仍在初始化中，避免状态错误或重复发放。
- 首次启动只让出事件循环，不再固定等待 32ms。失败重试和首帧后兼容尺寸刷新保留 32ms 延迟。
- Canvas 尺寸未变化时不重设宽高；viewport 和安全区未变时不重复绘制，宿主异常重设尺寸后仍可恢复。

## 本地检查

```powershell
npm run check
npm run check:release:strict
```

发布审计的包体统计现在应用 `project.config.json` 的排除规则，并检查运行时必需资源是否被误排除。优化前旧审计为 1,665,407 字节；本次约 938KB（916KiB），减少约 44%。这是本地待发布文件合计，不是微信服务器压缩后的下载包大小。

重新生成音乐源文件后，需要重新编码 MP3；编码器仅用于构建，不随游戏发布：

```powershell
npm run generate:audio
python scripts/compress-audio.py --lame "<本机 libmp3lame 动态库路径>"
npm run check:assets
```

也可使用系统能发现的 libmp3lame，省略 `--lame`。MP3 检查会验证逐帧格式、体积以及去掉编码延迟/填充后的有效采样数。

## 真机复测

在开发者工具导入本目录并重新编译，使用同一台手机、同一微信/基础库版本和网络，分别记录首次下载、有缓存冷启动、后台恢复。每组至少 10 次，比较中位数和 P90，同时记录是否为新存档。后台恢复与完整启动分开统计。

运行时增加 `getStartupTimings()`；可在开发者工具 `game.js` 的运行时创建后设置断点，或在调试调用方持有运行时引用读取。未新增生产全局调试对象、日志或上传。时间点单位均为毫秒，相对 `game.js` 开始执行；入口前的微信环境准备不在该计时范围。

| 字段 | 含义 |
| --- | --- |
| modulesReady | 入口 require 完成 |
| runtimeStarted | 运行时构造开始 |
| canvasReady | Canvas 和渲染器就绪 |
| storageReady | 存档读取及规范化完成 |
| runtimeReady | 输入布局和运行时初始化完成 |
| homeSubmitted | 首页绘制和输入布局提交完成 |
| preloadsStarted | 延迟图片/广告预加载均已发起 |
| retries | 入口构造重试次数 |

`homeSubmitted` 不等于 GPU 实际上屏；`preloadsStarted` 不等于图片解码或广告加载完成。用相邻时间点差值定位业务初始化开销，同时以微信诊断报告的首屏指标为准。

复测目标：首屏渲染准备向 320ms 收敛，代码包下载低于原 1016ms；总启动 4100ms 是验证目标，尚无优化后的真机数据。另需在 iOS/Android 各检查音乐连续循环、静音及前后台恢复，确认设备播放器正确处理 MP3 的延迟/填充信息。
